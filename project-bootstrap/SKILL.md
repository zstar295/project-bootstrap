# 从项目目的到可执行项目

将用户的目标落成一个可交给后续执行者的本地项目。交付应包含真实路径、输入来源、已实现的启动命令、验收标准、当前进度和后续工作包；完成程度由证据说明。

只读取当前环节需要的参考。实际项目的技术方法由领域证据和相关专业skill决定；本skill负责把方法、输入、环境、责任与验收组织成可执行工作。

## 工作流程

1. **确认项目位置与实际状态。** 使用用户指定目录；未给目录时先识别当前工作区，位置会影响写入时问清。检查入口、Git、已有数据/环境及正在执行的任务。读取现有规则并保留已确认决定。已有项目先做差距清单和具体修改，不覆盖旧入口或历史。
2. **收敛目标。** 提取最终成果、使用对象、成功证据、资料、资源、期限和授权范围。能从会话/文件查到的信息不重复询问；只问会改变路线或阻止执行的缺项，通常一批1～3问。假设和可选项独立记录；不以主观“理解95%”代替明确的完成条件。
3. **设计最小可行路线。** 写清目标→证据/输入→方法→产物→验收的联系；列出前后依赖、第一项可执行任务及升级条件。科研区分数值稳定、实验吻合、推断和预测；软件区分安装、测试、业务验收和发布。不同领域按其证据调整。需要选工具时核查官方文档/维护仓库，兼容性、许可证、资源和现有替代方案；仅安装路线确实需要的工具。
4. **实际搭建。** 新项目采用已审查manifest和[scripts/bootstrap_project.py](scripts/bootstrap_project.py)，先预览再`--apply`；已有项目按最小改动整合。脚本只生成通用控制框架，环境安装与领域实现继续按任务书完成。创建本地依赖隔离、实际环境记录、短入口、章节索引、工作单、状态、任务/经验记录与必要领域目录。依据[搭建流程](references/build.md)检查生成文件，替换仍不适用的项目方案。
5. **让首个任务可执行。** 实现它需要的最小程序/操作链路，核实输入、软件版本与命令，并在授权和资源允许的范围内运行小样例。未知许可证/数据/技术门明确记录；有局部缺口就先交付可执行的资料审查或环境工作包。不能把“计划写脚本”描述为已有程序。
6. **验收和交接。** 运行projectctl的`check`、project_doctor及与首包相关的领域检查；Git只记录本次文件，保存来源与失败证据。交付入口、已验证命令、当前就绪层级和具体下一包。按项目的实际授权继续任务；搭建请求本身不自动触发生产计算、发布或消息发送。

## 不变量

- 短AGENTS与索引说明“去哪里找”，方法、工作单、记忆与历史按需加载。日志不持续堆进入口。
- 原资料、已有代码和其他任务的修改保留。用户当前指令优先于历史；冲突有来源地修订。
- 初次搭建的内容绑定真实用户请求；通用脚本只能检查原句与哈希，无法鉴别人类身份。候选经验不自动成为正式长期知识，重大方法/方向判断需具体人类确认；常规局部实现按已有授权自主处理。
- 角色由任务分工决定，未指定时用planner/reviewer/executor的职责，不默认某个模型或自动建立其他聊天。跨产品共用本地文件，明确加载入口，不能假设自动发现。
- “框架生成”“环境可用”“首包可执行”“领域验收通过”分别报告。目录、版本记录和检查通过不能冒充最终项目成果。
- 初始化器拒绝覆盖和目录逃逸；不得增加`--force`或绕开项目护栏来完成整合。遇到碰撞先审查已有内容并做可追溯修改。

## 调用样例

用户可以只给目的开始：`使用 $project-bootstrap。项目目的：……；目录：……；已有资料：……；请补齐必要需求并实际搭建。`

详尽输入示例在[manifest.example.json](assets/manifest.example.json)。它是演示项目，非用户实际批准；由AI根据当前项目生成manifest，不要求用户填JSON。生成命令以`--help`为准；脚本使用Python 3.10+标准库。
