# 实际搭建与整合

## 新项目

先让AI生成manifest，将当前真实请求和已确认来源原句填入，不让用户承担JSON填表。参考assets/manifest.example.json；该文件只是测试演示，不可套用为真实人类批准。

```text
python -X utf8 <skill>/scripts/bootstrap_project.py --manifest <manifest.json> --root <project>
python -X utf8 <skill>/scripts/bootstrap_project.py --manifest <manifest.json> --root <project> --apply
```

默认预览生成文件清单与碰撞；没有force参数。先检查manifest中的目的/约束/工作单是否符合真实用户要求，再apply。任何输出碰撞均在写文件前报错；根目录可含无碰撞的其他文件，但有既有控制框架时走整合。

生成内容包括短AGENTS、spec、按章节索引、状态、工作单、输入清单、环境检查、配置化角色策略、追加任务/经验与来源批准、两个项目过程skill。按domain附加执行者目录权限；只在实际产物需要时建立业务目录。所有路径和模型职责来自项目，案例的物理参数/软件不会复制。

生成器不会自动安装软件、运行manifest中的命令或操作Git。继续做当前任务所需的环境/领域实现，更新环境记录和已验证命令，完成首包检查后再交付。没有技术代码链路的项目也可用明确操作、输入/责任与验收形成执行包。

## 已有项目

读现有AGENTS/索引/状态与最新任务事件。里程碑可能滞后，核对实际证据；不要把旧状态中的未获得当当前事实。Git已有修改或他人任务时先确定所有权，不reset、不覆盖、不一次git add整个仓库。

只补缺项或改冲突项，准备具体差异并按当前授权/治理落地。初始化器的碰撞拒绝不是停止任务的理由，可改为人工整合。保持原资料、来源请求、旧候选及已批准记录；不存在的原始数据/测试/技术判断不补造。一个项目只保留一份公共事实源。

## 环境和工具

盘点实际操作系统、解释器、版本、核心依赖、CPU/内存/磁盘和外部软件/许可。工具未使用过时记录not_tested；二进制存在只证明存在。实际小运行或版本/输出检查才能支撑其对应的通过范围。

优先现有适用工具及项目内隔离环境。安装确实必要的依赖后锁定实际版本并保留来源；不要改系统许可变量或全局运行时来套用模板。软硬件/领域skill只在对应项目需要时适配。长期配置以相对项目路径为主，主机绝对路径在environment.local.json覆盖。诊断器只检查声明工具的存在/版本元数据，不自动执行未知程序。

## Git与移植

已有Git保持身份/分支/远程配置；新仓库本地初始化，缺提交身份时用透明的本仓库自动化身份，不冒用用户身份。只提交本次明确文件。先记录真实来源与初始具体内容批准，再启用hook和提交。批准与role是流程证据，不认证人类或提供操作系统身份隔离。

配置命令为项目`scripts/configure_project_git.py --root <project>`；它只修改该仓库local hooksPath和project.python（运行配置脚本的实际解释器）。避免仅凭python3命令名选到Windows应用别名；在本项目实际环境中运行配置。克隆不继承local config，换主机后重新执行配置并核实环境。大型结果/软件目录按实际策略排除；将体积预算、输入/结果哈希和原始输出清单保留，移植时另带被忽略的必需资料。

## 验收层次

| 层次 | 证据 | 可声称 |
|---|---|---|
| 框架初始化 | 文件/章节/来源/角色检查 | 可读取与登记任务 |
| 环境可用 | 解释器、实际依赖/版本及需要的许可/试算 | 被检查工具链可用 |
| 首包可执行 | 输入/依赖齐备，已实现命令或明确操作，小样例/操作链路通过 | 可按该工作包开始 |
| 领域任务通过 | 工作单对应技术/业务/科学验收证据 | 仅相应结果通过 |

project_doctor输出首包前提及仍需领域小样例的状态，不能证明尚未实施的目标结果。readiness_report由AI根据真实检查填写，带命令、退出码/检查结果、产物和缺口。只有满足前三层中本项目实际需要的条件，才称“可执行项目”；否则明确指出已经能执行的早期包和关键缺项。
